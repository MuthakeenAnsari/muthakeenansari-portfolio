Personal operating-system project · Active development

NGIULS: Next Generation Interconnected Universal Linux System

Also branded “Universal Linux” · Development line 0.3.0

NGIULS is my ongoing Debian-based operating-system project. It builds on Debian GNU/Linux 13 and KDE Plasma, adding a custom package-management layer called UPM (Universal Package Manager), application and environment metadata in SQLite, system profiles and themes, AppArmor policy, locally packaged NGIULS components, and a Debian live-build/debootstrap ISO pipeline. The goal is to make software from different ecosystems easier to discover, install and launch through one understandable interface, while keeping the actual environment explicit instead of pretending every application is a native Debian package. The project is evolving, so features and compatibility are described according to their current implementation and evidence.

The problem NGIULS explores

Linux applications arrive through different package formats, repositories and runtime environments: Debian packages, Flatpak, AppImage, tools from other distributions, or Windows applications. Moving between unrelated instructions makes discovery and management harder. NGIULS explores one entry point that evaluates these choices, selects an appropriate available route, and explains what it is doing.

UPM in plain English

UPM is a Rust 2021 command-line application with a SQLite-backed registry. It is not just an alias for apt: it models several backends and environments, then makes a choice using source availability and compatibility evidence. It can explain its decision and accept an explicit backend choice. It stops visibly on failure; automatic fallback happens only when requested or configured.

How UPM decides

This is the architectural flow, not a promise that every route exists for every application.

  1. Find the applicationResolve the requested app name and its aliases.
  2. Gather evidenceCheck sources, package metadata, runtime needs, compatibility records and environments.
  3. Choose a routePick an appropriate available backend based on evidence and the backend decision order.
  4. Handle privileges carefullyRequest admin permission only where required; Wine-prefix operations stay with the desktop user.
  5. Install or launchRun the operation through the selected real backend or environment.
  6. Verify the outcomeInspect package, database, binary or Windows-executable evidence rather than trusting an exit code alone.
  7. Record the stateTrack applications, sources, environments, transactions and diagnostics in SQLite-backed state and logs.

Package formats and environments

  • Native Debian: APT/dpkg on Debian 13 is the system base.
  • Flatpak and AppImage: additional application packaging routes; AppImages are managed in a per-user NGIULS location.
  • Distrobox containers: provide separate environments for software from other Linux distributions without pretending their packages are native Debian packages. Four environments were validated on the development host: Arch (pacman), Fedora (dnf), Alpine (apk) and Kali (apt-get), each checked against its own /etc/os-release.
  • Optional backends: Snap and Homebrew code exists, but they were not installed in the examined setup.

Windows application support through Wine

NGIULS includes a Wine-based path for trying to run some Windows applications without requiring a Windows virtual machine, Windows installation media, or a separate Windows installation as part of the design. Its source contains PE/MSI detection, Wine-prefix lifecycle management, desktop launchers, runtime support, and DXVK/VKD3D graphics translation where appropriate. UPM also models compatibility evidence for individual Windows apps.

Compatibility varies by app. Some programs may install and launch; others may fail because they depend on unsupported Windows APIs, kernel drivers, anti-cheat systems, proprietary services or specific hardware. No claim is made that every .exe or .msi works. macOS application support remains exploratory, with no working support claimed.

SQLite, reliability and trust

SQLite is used as the registry and state store. The reported setup includes transactional schema migrations through version 15 and records for applications, packages, aliases, runtime dependencies, launchers, transactions, Windows compatibility, Wine prefixes, environments, profiles, sources and metadata. System-level and per-user state are kept distinct.

  • Prefer known sources and explain routing choices.
  • Verify the actual target environment, including container identity.
  • Report failures honestly rather than showing false success.
  • Use transaction logs and snapshot/rollback-related components where supported.
  • Distinguish code implementation from features verified on the current machine.

Security design

AppArmor policy and privilege separation form part of UPM’s design. System-changing operations use the appropriate privileges, while desktop-user Wine operations should not create root-owned user prefixes. NGIULS is not presented as audited or fully hardened.

Desktop, profiles, themes and ISO

NGIULS adds branding and personalization on top of KDE Plasma 6 and Qt6: profile and theme definitions, login and boot visuals, NGIULS meta-packages in a local signed APT repository, and an ISO build pipeline based on Debian live-build and debootstrap. The source tree also holds a Python/PyQt6 control-center design and helper tooling; some elements exist in source but were not deployed on the inspected installation, so they remain development work rather than finished user-facing features.

Planned · Not yet built

Hardware-adaptive local AI

The long-term plan is to integrate a local AI assistant into NGIULS. Instead of assuming every computer can run the same model, it would inspect available CPU capability, RAM, GPU/VRAM and runtime support, then select or recommend a suitable open-source model and configuration for that machine. The goal is to combine useful open-source AI resources into one local experience and allow selected system-customization tasks where hardware allows it. It should adapt for modest devices rather than requiring the strongest GPU, and it must be honest when a model is too large for the available resources.

This is a planned direction, not a completed feature. “Combining open-source resources” does not mean running every model simultaneously or guaranteeing all models will work on every computer.
